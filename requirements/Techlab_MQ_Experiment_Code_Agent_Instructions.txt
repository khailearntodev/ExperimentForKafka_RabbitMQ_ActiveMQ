TECHLAB DEV INTERVIEW 2026
MESSAGE QUEUE POC & BENCHMARK
INSTRUCTIONS FOR CODE AGENT

1. OBJECTIVE
Build a small, reproducible Proof of Concept to compare:
- RabbitMQ
- Apache ActiveMQ
- Apache Kafka

The goal is NOT to build a complete e-commerce system.

The PoC must answer:
- Does asynchronous messaging solve the main problem in the task?
- How do the three brokers behave under the same workload?
- Which solution is the best fit for the stated requirements?

Do not assume a winner before testing.

2. SOURCE SITUATION
System:
- ~500,000 registered users
- ~50,000 DAU
- ~3,000–5,000 orders/day
- Expected growth: 3–5x in 12–18 months
- Microservices, Docker, Kubernetes

Main services:
- API Gateway
- Order Service
- Payment Service
- Inventory Service
- Notification Service
- Analytics Service

Current communication:
- Synchronous HTTP REST.

Problems from the task:
- Order creation may time out when Payment is slow/unavailable.
- Notification increases Order response time.
- Analytics can degrade performance during traffic spikes.
- Services are tightly coupled.
- Retry logic is complex and duplicated.

Relevant requirements:
- Order Service must respond quickly without being blocked by downstream services.
- Payment may be slow/fail and requires retry.
- Inventory is sensitive to race conditions under high concurrency.
- Notification does not require strict real-time delivery.
- Analytics must not affect the critical user flow.

3. EXPERIMENT SCOPE
Keep the PoC small.

Implement only:
1. Order Service
2. Payment Worker/Service
3. One broker at a time:
   - RabbitMQ
   - ActiveMQ
   - Kafka
4. Load generator / benchmark tool

Do NOT build full Inventory, Notification, Analytics, API Gateway, database,
or Kubernetes implementations for the PoC.

The experiment focuses on:
- Order not being blocked by slow Payment.
- Payment failure and retry.
- Basic message processing performance.

Order Service MUST NOT synchronously call Payment.

Expected flow:
Client -> Order Service -> publish message -> HTTP 202 response
-> Payment Worker consumes -> Payment processes asynchronously.

Payment must support:
- normal processing
- configurable delay
- controlled failure followed by retry

5. APPLICATION DESIGN

5.1 Order Service
Expose:
POST /orders

Example request:
{
  "orderId": "ORD-001",
  "userId": "USER-001",
  "amount": 100000
}

Behavior:
1. Receive request.
2. Create OrderCreated event.
3. Publish to broker.
4. Do not wait for payment.
5. Return HTTP 202 Accepted.

Example response:
{
  "orderId": "ORD-001",
  "status": "PROCESSING"
}

5.2 OrderCreated message
Use the same payload for all brokers:

{
  "eventId": "UUID",
  "orderId": "ORD-001",
  "userId": "USER-001",
  "amount": 100000,
  "eventType": "ORDER_CREATED",
  "timestamp": "..."
}

Use JSON. Do not change payload between brokers.

5.3 Payment Worker
Consume OrderCreated.

Configurable behavior:
- PAYMENT_DELAY_MS
- controlled failure mode

Example:
- delay = 0
- delay = 3000
- fail first 2 attempts, succeed on attempt 3

Record:
- message received
- processing started
- processing succeeded/failed
- retry attempt
- processing completed

6. BROKER ABSTRACTION

Use a common abstraction so business logic stays unchanged.

Conceptually:

MessagePublisher
  +-- RabbitMqPublisher
  +-- ActiveMqPublisher
  +-- KafkaPublisher

Use a configuration such as:
MQ_TYPE=rabbitmq
MQ_TYPE=activemq
MQ_TYPE=kafka

The exact implementation is flexible, but application/business logic must
remain equivalent across brokers.

7. BROKER SETUPS

RabbitMQ:
- Docker container
- Simple exchange/queue/routing-key model
- Example:
  exchange: order.exchange
  queue: payment.queue
  routing key: order.created

ActiveMQ:
- Docker container
- Simple destination/queue for OrderCreated -> Payment Worker

Kafka:
- Docker-based Kafka setup
- Topic: order.created
- One consumer group for Payment Worker

Record broker versions in README.

8. FAIRNESS RULES

All brokers must use:
- same Order Service
- same Payment Worker logic
- same message payload
- same test data
- same load generator
- same request count
- same concurrency
- same payment delay
- same failure behavior
- same number of repetitions
- same machine/environment

Only broker implementation/configuration should differ.

Record:
- broker version
- application/runtime version
- machine CPU/RAM
- test parameters

Do not optimize one broker heavily while leaving others at defaults unless
the difference is documented and justified.

9. TEST SCENARIOS

TEST 1 - NORMAL WORKLOAD
Purpose: baseline comparison.

Suggested:
- 1,000 orders
- 50 concurrent users
- Payment delay: 0 ms
- Payment failure: disabled

Run all three brokers.
Recommended: 3 runs per broker.

Collect:
- average Order response latency
- p95 Order response latency
- throughput
- error rate

TEST 2 - SLOW PAYMENT
Purpose: directly test whether Order is blocked by slow Payment.

Suggested:
- 1,000 orders
- 50 concurrent users
- Payment delay: 3,000 ms
- Payment failure: disabled

Optional baseline:
Run the same scenario with synchronous HTTP:
Order Service -> Payment Service -> response.

For each broker collect:
- average Order response latency
- p95 Order response latency
- throughput
- timeout/error rate

The key metric is Order response latency, not total payment completion time.

TEST 3 - PAYMENT FAILURE AND RETRY
Purpose: test retry/failure handling.

Suggested:
- 100 orders
- 10 concurrent users
- Payment fails on attempts 1 and 2
- Payment succeeds on attempt 3

Use equivalent retry behavior for all brokers.

Collect:
- successful payments
- failed messages
- retry count
- lost messages, if any
- total processing time
- final success rate

Do not compare one broker with automatic retries against another with no
retry mechanism. Retry behavior must be equivalent.

10. TEST METRICS

Primary:
1. Average Order Response Time
2. P95 Order Response Time
3. Throughput
4. Error/Timeout Rate
5. Retry Success Rate

Optional:
- CPU
- memory
- message processing time

11. TEST EXECUTION

For each broker:
1. Start broker and required application services.
2. Verify health.
3. Clear previous messages/data.
4. Start Payment Worker.
5. Run scenario.
6. Collect benchmark output.
7. Save logs/metrics.
8. Repeat 3 times.
9. Stop broker/application.
10. Move to next broker.

Matrix:
- 3 brokers
- 3 scenarios
- 3 runs each
- Total: 27 benchmark runs

If execution time becomes an issue, reduce workload while keeping conditions
identical across brokers.

16. WHAT THE EXPERIMENT SHOULD PROVE

The experiment should provide evidence about:
- asynchronous order processing
- Order Service response latency
- behavior under slow Payment
- basic throughput under the tested workload

The experiment should NOT claim to prove:
- production-scale performance
- Kubernetes-scale behavior
- absolute maximum throughput of any broker
- universal superiority of one broker
- complete Inventory race-condition handling
- complete Analytics architecture
